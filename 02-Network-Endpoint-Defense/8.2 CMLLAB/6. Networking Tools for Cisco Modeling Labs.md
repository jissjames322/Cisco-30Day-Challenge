
# Introduction

Cisco Modeling Labs (CML) offer a range of supporting tools that expand the lab functionality. The external connector feature enables external connectivity to and from lab nodes to the outside networks. You can use this functionality to allow outbound connectivity and thus enable software updates or patches from the internet. Alternatively, you can use this tool to provide inbound access, allowing external management systems to control the virtual lab devices. Other useful networking tools include the link packet capture, the WAN emulator, and the Cisco TRex traffic generator.


## Use External Connector in NAT Mode to Enable Outbound Internet Connectivity

## Scenario

Cisco Modeling Labs offer a wide range of options for exploring network technologies. Suppose that you need to provide external connectivity to your lab nodes. You may need to **enable external connectivity to your Cisco Modeling Labs environment.** There are two methods of providing internet connectivity, using **bridge mode** and **Network Address Translation (NAT) mode:**

- **Layer 2 bridge mode** allows inbound connectivity. Common examples are management connectivity from external systems, which may or may not include provisioning systems such as **Ansible or products like Nexus Dashboard and Catalyst Center.**
    
- NAT mode is used to provide outbound connectivity that is initiated from the lab devices. Typical use cases include **lab devices that download software or patches from the internet or connect to some external database. You will implement NAT mode in this lab.**

## Task 1: Verify the Initial State

In this task, you verify the initial state, without the External Connector.

1. Log in to the Cisco Modeling Labs WebUI using the Chrome browser.
2. Make sure that your basic topology is loaded. Start the lab if needed.
3. Right-click **PC1** and open its console. Click the **OPEN Console** button and log in with the username **cisco** and password **cisco**.
4. Verify the PC1 IP addressing using the `ip addr` command.
5. Verify the PC1 routing table using the `route` command.
6. From PC1, ping the router (10.0.1.254) to verify the initial connectivity within the local subnet. Optionally, ping other systems, such as PC2 (10.0.2.1 or cisco.com) to verify that neither connectivity to other subnets nor external systems is possible.

Connectivity to PC2 and to cisco.com fails for two different reasons. PC2 belongs to a different subnet and PC1 needs to be configured with a default gateway to reach it. PC1 cannot reach cisco.com because there is no external connector. Next, you will provide that external connectivity.

7. View the PC1 DNS setup.
```
PC1:~$ cat /etc/resolv.conf
cat: can't open '/etc/resolv.conf': No such file or directory
```

There are no initial DNS settings on the endpoint.


## Task 2: Enable External Connectivity in NAT Mode

In this task, you attach an external connector in NAT mode to provide outbound connectivity from PC1 and any endpoints attached to Switch1. The traffic flow from a PC in the internal lab to the outside is depicted below:

8. Select **Add Nodes** and choose the **External Connector**. Drag and drop it near Switch1, as you will attach the connector to it.

You may attach an external connector to any device, for example directly to PC1. Connecting it to a switch, however, offers the advantage of providing external connectivity to all devices in the Layer 2 domain. You can add as many External Connector nodes as you want, each using any of the available modes (NAT or Layer 2 Bridge). You can, for example, connect each node directly to an external network. In this case, however, you connect the external network to Switch1, which will then provide common external access to the attached endpoints.

9. Click the external connector. In the **Config** tab, click in the mode configuration field and examine the available options. Keep the default mode (NAT).

Apart from the mode (NAT or system bridge), you also see the adapters that provide the external connectivity. The following figure is from the Cisco Modeling Labs Cockpit UI. This is the administrative UI, where Cisco Modeling Labs logs issues and allows for management of the deployment. The Cockpit is covered more in additional Cisco U training courses.

The Networking section exists in case you are adding more adapters to the CML vm, or if you wanted to allow your Cisco Modelings Server to honor vlan tagging from your physical network into the lab environment using an External Connector.

![[Pasted image 20261111135835.png]]

A CML VM may have two or more virtual adapters (vNICs). This example shows a virtualized host and a CML VM with three vNICs:

![[Pasted image 20261111135845.png]]

The vNIC in NAT mode maps to virbr0. The external connector in NAT mode actually operates in Port Address Translation (PAT) mode, translating the internal addresses and TCP/UDP ports to different ports on the global address of virbr0.

In this example, the virbr0 address belongs to a private IP address range and therefore an additional external address translation is needed for Internet access.

Cisco Modeling Labs software only recognizes certain bridge device names as intended for use as external connectors. Any name that falls outside the recognized patterns is ignored and may be used for other purposes on the host. The recognized bridge device names have two parts:

- The intended kind of bridge: bridge, VLAN, virbr, bond, team, or local.
    
- One to four digits 0 to 9.

10. Choose the connector's **Settings** tab, rename the node to **ext-conn-nat** and apply the change.

The Node Name does not have any relevance to the node functionality. It is only used to identify the node.

Note that the external connector does not have any customizable configuration, other than the mode. In Layer 3 NAT mode, the Cisco Modeling Labs VM performs dynamic NAT for Layer 3 traffic initiated by lab nodes. The default subnet is 192.168.255.0/24, and lab nodes should be configured for DHCP on the connected interface. The traffic is ultimately routed out of one of the controller host’s virtual network interfaces (vNIC) using that host’s own routing configuration.

11. Right-click the connector and choose **Add Link**. Connect the link to Switch1, to the first available interface (Gigabit0/2 in this example).

12. Right-click the connector and start the node.

13. In the console of PC1, add a DHCP-derived IP address to the network adapter.
14. Verify the obtained IP address.
15. Ping cisco.com to verify internet access.


Which functional components does the external connector comprise?

16. View the routing table on PC1.
17. When attaching an external connector to the lab nodes, use nondefault routing for internal connectivity, to avoid route ambiguities. In this scenario, you may use the following commands to install specific static routes on PC1 and PC2, enabling connectivity between them:

```
PC1:~$ sudo route add -net 10.0.2.0 netmask 255.255.255.0 gw 10.0.1.254

PC2:~$ sudo route add -net 10.0.1.0 netmask 255.255.255.0 gw 10.0.2.254

```


18. Verify the PC1 DNS setup.

Although the connector mode (NAT) indicates that NAT-based communication is expected, the node provides several automatic functions out-of-the-box: DHCP, NAT, and DNS. Attaching the connector to a switch rather than an endpoint allows you to share the external connection among multiple endpoints in a bridge domain. This verification completes the lab, great job!
