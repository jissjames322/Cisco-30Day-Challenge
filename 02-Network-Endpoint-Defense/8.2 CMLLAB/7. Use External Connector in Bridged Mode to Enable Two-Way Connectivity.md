
## Scenario

There are two methods of providing **external internet connectivity, using Network Address Translation (NAT) mode and the bridged mode.**

**Layer 2 bridge mode also allows inbound connectivity**. Common examples are management connectivity from **external systems, such as Ansible, along with network controllers like Nexus Dashboard and Catalyst Center**. Bridged Mode is also useful when you want to peer with external devices using routing protocols like **Open Shortest Path First (OSPF)**, or when using your own **DHCP server to provide IP addressing**. You will implement t**his mode in this lab, enabling two-way traffic flow, as shown below.**


![[Pasted image 20261111142707.png]]


This connectivity model supports both DHCP and static IP addressing. In the first approach, you would typically have an external DHCP server serving the bridged network, either directly connected to it, or reachable via DHCP relays. In this lab, you will use static IP addresses.


The connectivity is provided over a vNIC operating in bridged mode, as shown below:

![[Pasted image 20261111142831.png]]
When designing external connectivity in Layer 2 bridge mode, you may choose the Unmanaged Switch, a small footprint virtual node that provides Layer 2 switching. It does not count toward the running node count license and does not consume dedicated CPU cores as resources. The Unmanaged Switch is recognized as a Linux bridge on the Cisco Modeling Labs server. Due to its minimal footprint, the Cisco Modeling Labs host can typically handle up to a few hundred Linux bridges running at the same time, depending on its size.

Notwithstanding the benefits of the Unmanaged Switch, you already have two Cisco switches in your lab topology, and you will reuse your second switch to provide outside connectivity over Layer 2.

11. Open a terminal window on your Student VM and verify the IP address on the network adapter (ens192).


Having identified the IP address in the external network (10.1.1.101), you will bridge this network over the external connector. You need to pick a free IP address to avoid any address overlaps, such as 10.1.1.99, and assign it to PC2. Before doing so, make sure that it is indeed unused.

12. Ping the address 10.1.1.99 to ensure its availability.

```
ping 10.1.1.99
```

13. Check the ARP table to verify that no host has been learned with the tested IP address.

ARP verification may be useful in environments where firewalls do not respond to ICMP echo requests or drop the echo replies.

```
student@student-vm:~$ arp -a
_gateway (10.1.1.1) at 50:0f:80:f0:d0:41 [ether] on ens192
? (10.1.1.20) at 00:50:56:89:ff:80 [ether] on ens192
```


14. Switch to the PC2 console, add the secondary IP address 10.1.1.99/24 to the network adapter.

```
PC2:~$ sudo ip addr add 10.1.1.99/24 dev eth0
```

Alternatively, you could add a dedicated NIC for connectivity via the external connectors. The benefit of this approach is a clear delineation: a dedicated NIC for "internal topology" traffic, and one for "external traffic."
